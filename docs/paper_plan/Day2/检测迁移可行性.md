# Day 2：检测迁移可行性验证

日期：2026-06-09。Day 2 是全周风险最高的一天，目标是验证三件事：是否能凑齐异构检测模型并进行相互比较，最小差分 oracle 是否能产出有意义的分歧信号，YOLO 的中间层是否能挂 hook。结论是三项验证全部通过。下面按 oracle 设计、pilot 数字和 YOLO 结论三部分记录。

实验全部在实验室服务器上运行。模型使用 torchvision 预训练权重，数据使用服务器上的 COCO val2017。脚本是 `scripts/pilot_det_oracle.py` 和 `scripts/probe_yolo_hooks.py`。

## 检测差分 oracle 设计

分类版 mfuzz 的差分机制依赖多个模型对同一张图的类别预测投票。检测任务更复杂，因为模型输出的是一组带框、带类别、带分数的检测，数量和位置都不固定，不能直接逐元素对齐。因此，检测差分的第一步是把不同模型的检测框在空间上对齐。对齐之后，才能判断一致还是分歧。

### 选三个异构模型

差分需要利用架构差异制造分歧，因此 pilot 选择了三种不同检测范式：

- Faster R-CNN（`fasterrcnn_resnet50_fpn_v2`）：两阶段，anchor-based。
- RetinaNet（`retinanet_resnet50_fpn_v2`）：一阶段，anchor-based。
- FCOS（`fcos_resnet50_fpn`）：一阶段，anchor-free。

三者都使用 torchvision 的 DEFAULT 权重，都在 COCO 上训练，并共享同一套 91 类标签空间（`weights.meta["categories"]`）。脚本加载时会逐一核对类别表是否一致；如果不一致，就直接报错，因为类别空间不一致时差分没有前提。三个模型都接受 `[0,1]` 的浮点张量作为输入，不需要各自的预处理流水线，因此可以省去一层适配。

### 不使用真值，使用跨模型一致性

pilot 不依赖 COCO 标注，oracle 完全建立在跨模型一致性上。这样设计的原因是，后面如果迁移到遥感数据，那里很可能没有现成标注；基于一致性的方案更容易迁移。具体流程分三步。

第一步是聚簇。把三个模型在一张图上的所有检测框放到一起，按 IoU 跨模型聚成簇，并用并查集求连通分量。同一个模型的两个框不互相合并。只有来自不同模型、且 IoU 超过阈值的框，才连接到一起。这样，一个簇就对应一个物理对象。

第二步是确定 consensus。一个簇里如果有至少两个不同模型的框，就认定它是一个 consensus 对象，相当于多数模型都认为这里有对象。簇的类别取多数票；票数并列时，取分数最高的类别。代表框取多数类别中分数最高的框。

第三步是逐模型判定失效。对每个 consensus 对象，观察每个模型相对它的表现，并归入四类失效：

- 漏检 miss：这个 consensus 对象中没有该模型的框。
- 虚检 spurious：该模型的某个框落在只有它自己的单点簇中，没有任何其他模型支持。
- 类别错误 cls：该模型在簇中有框，但类别和多数票不一致。
- 定位偏移 loc：类别一致，但框与代表框的 IoU 偏低，落在 `[iou_thr, loc_thr)` 区间。

cls 和 loc 是两个独立标志，可以同时为真，对应 TIDE 中的 both，不单列第五类。pilot 阈值设置为：score 下限 0.5、聚簇 IoU 0.5、定位偏移 IoU 0.7。

### oracle 的已知局限

没有真值时，oracle 无法区分两种情况：某个模型多检了一个假框，或者另外两个模型一起漏掉了一个真目标。因此，被判为 spurious 的框，可能是少数模型正确、其他模型错误。这是一致性方案的固有限制。COCO 上有现成标注（`datasets/coco/annotations`），后续可以用真值做一次 TIDE 式校验，把"多数对少数错"和"少数对多数错"区分开。遥感数据如果没有标注，这个局限需要在论文中说明。

## Pilot 真实数字

实验在 40 张 COCO val2017 图上运行，阈值如上。结果可复现，重复运行数字不变。

```
图像数 40    consensus 对象 224    三模型完全一致 124    完全一致占比 55.4%

模型                  漏检    虚检   类别错   定位偏     一致
faster_rcnn          6     147       3       2     213
retinanet           68       4       1      12     143
fcos                 7      23       5      14     198
```

先看分歧强度。224 个 consensus 对象中，只有 124 个三模型完全一致，占 55.4%。剩下接近一半的对象上，三个模型至少在某一点上不一致。这个分歧信号足够强，说明不同架构确实能在同一张图上产生大量可观测的不一致，检测差分 oracle 具备可行性。

再看分歧结构。三个模型各有偏向，而且偏向与架构相符。Faster R-CNN 的虚检达到 147，明显高于另外两个模型，说明这个两阶段模型更倾向于给出更多检测框。RetinaNet 正相反，漏检达到 68，是三个模型中最保守的，更倾向于少检。FCOS 居中，虚检 23、漏检 7，表现为 anchor-free 的折中结果。类别错误在三个模型上都很少，都是个位数，说明只要框能对齐，类别判断高度一致。分歧主要来自"这里到底有没有对象"和"框是否足够准确"，而不是"这是什么类别"。

这一结果对论文主要叙述有利。三个模型的失效不是随机噪声，而是与架构系统相关。这是后续做结构归因的前提。如果分歧完全随机，归因就没有明确对象。

虚检和漏检存在一个盲点：Faster R-CNN 的 147 个虚检中，有一部分很可能是它正确、另外两个模型共同漏检。这个问题需要后续真值校验厘清，但不影响 Day 2 的结论：分歧信号强，并且与架构相关。

## YOLO 中间层访问结论

YOLO 作为架构多样性补充，需要单独验证内部可访问性。差分 oracle 只使用最终检测框，因此任何检测器都可以作为黑盒参与投票；但研究内容 2 的关键神经元和中间层覆盖要求能取到中间激活，因此模型必须暴露可以挂 hook 的子模块。脚本是 `scripts/probe_yolo_hooks.py`，模型使用 `yolo11n.pt`，ultralytics 版本是 8.4.62。

Ultralytics 的 `YOLO` 是封装对象，真正的网络是 `YOLO.model`，类型为 `DetectionModel`，确认是标准 `nn.Module`。整个网络有 319 个子模块，其中 88 个是 Conv2d。在 Conv2d 层中从浅到深均匀采样 8 个层并挂 forward hook，执行一次预测后，8 个 hook 全部触发并取到激活。激活形状从浅层的 `(1, 16, 224, 320)` 到深层的 `(1, 256, 14, 20)`，覆盖骨干、neck 和检测头。

有一个细节需要记录。第一次尝试时，在叶子模块上无差别采样，结果 8 个 hook 中只有 3 个触发，未触发的都是 BatchNorm2d。原因是 ultralytics 推理时会把 Conv 和 BN 融合（auto-fuse）。融合之后，BN 模块被旁路，它的 forward 不再调用，hook 自然不触发。这不是访问受限，而是融合后的正常结果。把挂点放在 Conv2d 上就能避开这个问题，而 Conv2d 输出本来就是神经元覆盖关注的激活载体。

结论是，YOLO 的中间层可以挂 hook 取激活，能够进入结构层分析，不必降级为纯黑盒 oracle。唯一需要适配的是层命名：YOLO 的命名是 `model.0.conv`、`model.23.cv3.1.0.0.conv` 这种风格，与 torchvision 的 `core/hooks.py` 自动发现逻辑不同。真正接入框架时，需要为 YOLO 编写一套层选择规则。这是工程适配，不是可行性障碍。

## 小结

Day 2 的三项验证全部通过。异构差分在检测任务上可行，分歧信号强且与架构系统相关；最小 oracle 的四类失效判定能产出可解释的数字；YOLO 中间层可访问，结构分析可以纳入 YOLO。贯穿全周的两条风险中，YOLO 内部访问风险已经解除，剩下的遥感数据集标签空间问题需要尽早评估，判断是否需要自训模型。下一步按计划进入 Day 3，把内部反馈机制映射到检测结构。
