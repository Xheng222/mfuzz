# Day 2：检测迁移可行性探路

日期 2026-06-09。这是全周风险最高的一天，目标是验证三件事能不能跑通：异构检测模型能不能凑齐并互比、最小差分 oracle 能不能产出有意义的分歧信号、YOLO 的中间层能不能挂 hook。结论是三件都通了。下面分设计、pilot 数字、YOLO 结论三块记录。

实验全部在实验室服务器上跑，模型走 torchvision 预训练权重，数据用服务器上的 COCO val2017。脚本是 `scripts/pilot_det_oracle.py` 和 `scripts/probe_yolo_hooks.py`。

## 检测差分 oracle 设计

分类版 mfuzz 的差分靠多个模型对同一张图的类别预测投票，检测要复杂一些，因为模型输出的是一组带框、带类别、带分数的检测，数量和位置都不固定，没法直接逐元素对齐。所以差分的第一步是把不同模型的检测框在空间上对齐，对齐之后才能谈一致还是分歧。

### 选三个异构模型

差分要靠架构差异制造分歧，三个模型特意挑了互不相同的检测范式：

- Faster R-CNN（`fasterrcnn_resnet50_fpn_v2`）：两阶段，anchor-based。
- RetinaNet（`retinanet_resnet50_fpn_v2`）：一阶段，anchor-based。
- FCOS（`fcos_resnet50_fpn`）：一阶段，anchor-free。

三者都用 torchvision 的 DEFAULT 权重，都在 COCO 上训练，共享同一套 91 类标签空间（`weights.meta["categories"]`）。脚本加载时会逐一核对类别表是否一致，不一致就直接报错，因为类别空间不一致差分就没有前提。输入这三个模型都接受 `[0,1]` 的浮点张量，不需要各自的预处理流水线，省去一层适配。

### 没有真值，靠跨模型一致性

pilot 不依赖 COCO 的标注，oracle 完全建立在跨模型一致性上。理由是后面要迁到遥测数据，那里大概率没有现成标注，靠一致性的方案能直接搬过去。具体分三步。

第一步聚簇。把三个模型在一张图上的所有检测框放到一起，按 IoU 跨模型聚成簇，用并查集求连通分量。同一个模型的两个框不互相合并，只有来自不同模型、IoU 超过阈值的框才连到一起。这样一簇框就指向同一个物理对象。

第二步定 consensus。一个簇里如果有至少两个不同模型的框，就认定它是一个 consensus 对象，相当于多数模型都同意这里有个东西。簇的类别取多数票，票数并列时取分数最高的那个；代表框取多数类别里分数最高的框。

第三步逐模型判失效。对每个 consensus 对象，看每个模型相对它的表现，归到四类失效：

- 漏检 miss：这个 consensus 对象里没有该模型的框。
- 虚检 spurious：该模型的某个框落在只有它自己的单点簇里，没有任何别的模型支持。
- 类别错误 cls：该模型在簇里有框，但类别和多数票不一致。
- 定位偏移 loc：类别对得上，但框与代表框的 IoU 偏低，落在 `[iou_thr, loc_thr)` 这段带里。

cls 和 loc 是两个独立的标志，可以同时为真，对应 TIDE 里的 both，没有单列第五类。阈值方面 pilot 取 score 下限 0.5、聚簇 IoU 0.5、定位偏移 IoU 0.7。

### 这套 oracle 的已知局限

没有真值时，oracle 分不清到底是某个模型多检了一个假框，还是其它两个模型一起漏了一个真目标。被判成 spurious 的框，有可能是它对、别人错。这是一致性方案天生的盲点。COCO 上有现成标注（`datasets/coco/annotations`），后面可以拿真值做一次 TIDE 式校验，把"多数对少数错"和"少数对多数错"区分开。遥测数据上没标注时，这个局限要在论文里讲清楚。

## Pilot 真实数字

在 40 张 COCO val2017 图上跑，阈值如上。结果可复现，重跑数字不变。

```
图像数 40    consensus 对象 224    三模型完全一致 124    完全一致占比 55.4%

模型                  漏检    虚检   类别错   定位偏     一致
faster_rcnn          6     147       3       2     213
retinanet           68       4       1      12     143
fcos                 7      23       5      14     198
```

先看分歧强不强。224 个 consensus 对象里只有 124 个三模型完全一致，占 55.4%，剩下接近一半的对象上三个模型至少在某一点上不合。这个分歧信号足够强，说明换不同架构确实能在同一张图上制造出大量可观测的不一致，差分 oracle 在检测上是立得住的。

再看分歧的结构，三个模型各有各的偏向，而且偏向和架构对得上。Faster R-CNN 的虚检高达 147，远超另外两个，说明这个两阶段模型倾向于多检，框给得最满。RetinaNet 正相反，漏检 68，是三个里最保守的，倾向于少检、宁缺毋滥。FCOS 居中，虚检 23、漏检 7，是 anchor-free 的折中表现。类别错误三个模型都很少（个位数），说明只要框对上了，类别判断高度一致，分歧主要出在"这里到底有没有东西"和"框得准不准"上，而不是"这是什么"。

这个结果对论文主线是好消息。三个模型的失效不是随机噪声，而是和架构系统相关的，这正是后面要做的结构归因的前提。如果分歧纯随机，归因就无从谈起。

要注意虚检和漏检的盲点：Faster R-CNN 的 147 虚检里，有一部分很可能是它对、另外两个一起漏，记到了它头上。这条要靠后面的真值校验去厘清，不影响今天"分歧信号强、且与架构相关"这个结论。

## YOLO 中间层访问结论

YOLO 作为架构多样性的补充，单独验证它的内部可访问性。差分 oracle 只用最终检测框，任何检测器当黑盒都能投票；但研究内容 2 的关键神经元和中间层覆盖要求能取到中间激活，这就要求模型暴露可挂 hook 的子模块。脚本是 `scripts/probe_yolo_hooks.py`，模型用 `yolo11n.pt`，ultralytics 版本 8.4.62。

Ultralytics 的 `YOLO` 是个封装，底下真正的网络是 `YOLO.model`，类型 `DetectionModel`，确认是标准 `nn.Module`。整个网络 319 个子模块，其中 88 个是 Conv2d。在 Conv2d 层里从浅到深均匀采样 8 个挂 forward hook，跑一次预测，8 个全部触发并取到了激活，形状从浅层的 `(1, 16, 224, 320)` 一路到深层的 `(1, 256, 14, 20)`，骨干、neck、检测头都覆盖到了。

中间踩到一个点值得记。第一次试的时候在叶子模块上无差别采样，结果 8 个里只有 3 个触发，没触发的全是 BatchNorm2d。原因是 ultralytics 在推理时会把 Conv 和 BN 融合（auto-fuse），融合之后 BN 模块被旁路，它的 forward 不再调用，hook 自然不触发。这不是访问受限，而是融合的正常结果。把挂点取在 Conv2d 上就绕开了这个问题，而 Conv2d 输出本来就是神经元覆盖关心的激活载体。

结论是 YOLO 的中间层可以挂 hook 取激活，能进入结构层分析，不必降级成纯黑盒 oracle。唯一要适配的是层命名：YOLO 的命名是 `model.0.conv`、`model.23.cv3.1.0.0.conv` 这种风格，和 torchvision 的 `core/hooks.py` 自动发现逻辑不一样，真正接入框架时要为 YOLO 写一套层选择规则。这是工程适配，不是可行性障碍。

## 小结

Day 2 三件事都验证通过。异构差分在检测上立得住，分歧信号强且与架构系统相关；最小 oracle 的四类失效判定能跑出可解读的数字；YOLO 中间层可访问，结构分析的范围可以把 YOLO 也纳进来。两条贯穿全周的风险里，YOLO 内部访问这条今天解除了，剩下遥测数据集标签空间那条还悬着，要尽早评估要不要自训模型。下一步按计划进 Day 3，把内部反馈机器映射到检测结构。
