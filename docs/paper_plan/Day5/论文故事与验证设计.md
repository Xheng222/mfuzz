# Day 5：论文故事与验证设计

日期 2026-06-10。全量结构分析出数之后，经讨论定下了论文的叙事结构、验证设计和接下来的工作顺序。本文记录这次讨论的结论，作为实验矩阵定稿前的设计依据。

## 三幕故事

论文按三步讲。第一步，我们有一个动态反馈驱动的框架，它发现检测模型的失效，并把失效定位到结构位置。第二步，我们用多种消融验证框架设计合理：能稳定产出数据和结果，观察式证据与干预式证据互相印证。这一步证明的是框架自洽，还不证明它有用。第三步，我们用外部的、独立于框架自身的手段，证明框架找到的缺陷确实存在，并且我们的方法更好。

前两幕是必做项。第三幕要谨慎推进，原因是我们目前还没有一个完全可信的失效模式判定方案：在逐实例的微观证据建立起来之前，模式层面的主张缺乏地基。

## 第一幕的硬前置

结构定位这半边已经全量跑通（见同目录的框架适配文档）。失效发现这半边还停在分类版，要把反馈循环在检测上转起来，需要完成：hooks 的多次调用累积（神经元单位变为层×尺度×通道）、profiling 换 NMS 前类别 logit 当归因目标、obj_1 改写为对 consensus 对象匹配分数的偏离、语义项的 v(x) 换成 backbone 或 FPN 特征、engine 的 Seed 换成共识对象集合。机制不动，换的是目标和数据结构。

## 第二幕的消融分组

分类版的消融基建直接继承：configs 里 diff、diff_cov、diff_sem、full 就是现成分组，λ2/λ3 置零、动态反馈开关、α 切频率与归因都不用新写。检测版新增的消融是结构分析特有的三组：观察式归因与干预式消融的印证（已有）、归因份额相对 agree 对照的比值（已有）、pilot 到全量的稳定性（已有）。还要补一组分数阈值按模型校准的对照，回应三模型分数标定不同的问题。

另有一个稳赚的实验：自然失效与 fuzzing 生成失效的结构分布对比。如果生成失效落在与自然失效相同的结构签名上，说明框架找到的是真实薄弱点；如果落在新位置，说明反馈驱动探到了静态分析够不着的区域。两种结果都有解释价值。

## 第三幕的正反验证

验证必须发生在模式层面，因为论文的主张是结构性的缺陷模式，不是单个失效实例。定下正反两条路。

正面验证：用独立的失效诱发手段，在同一批模型上诱发失效，跑同一套结构归因，看结构签名是否收敛。诱发手段选 COCO-C 风格的腐蚀变换（模糊、噪声、天气），或按真值属性筛出的困难子集（小目标、遮挡）。这个设计的关键好处是腐蚀图像带真值，失效判定可以直接用真值而不依赖差分 oracle——诱发手段和裁判都换掉了，签名仍收敛的话，一次实验同时给 oracle 可靠性和签名真实性背书。比较必须用条件分布（给定失效类型看结构分布），因为不同诱发手段产生的失效类型比例本来就不同。

反面验证：按缺陷类型做针对性修复，验证错误率下降。设计的关键在对照组：只解冻责任结构桶微调，对比同参数量、同步数下只解冻一个非责任桶微调。如果前者对该类失效的削减显著更多、且整体 mAP 不退化，定位的因果性才算坐实。验证端用双重标准：我们的差分框架计数，加上外部诱发方案下的计数。这条成本主要在微调，放在最后做，前提是失效模式已经可信。

## 当前瓶颈：报告太宏观

现在的输出报告只有聚合指标，缺微观原始数据。JSON 里的逐实例记录有图名、失效类型、consensus 类别、责任层级、落框标志、逐桶份额，但没有框坐标和分数、没有 consensus 簇的上下文（其它模型在同一位置判了什么）、没有空间峰值坐标、没有任何可视化。结果是拿到聚合表之后，无法回到任何一个具体失效上问"这真的是缺陷吗"。

要做的升级：逐实例记录补全检测框、分数、簇内全部模型的检测；每个失效实例落一张标注图，画上目标模型的框、consensus 代表框、其它模型的框、责任层级的梯度×激活热力图与峰值位置，按失效类型分文件夹存放。有了微观证据，先人工抽查一批实例，确认 oracle 判定和归因指向可信。可靠性从实例层面建立，不靠声明。

这项升级当天已完成并重跑了全量：逐实例 JSON 带齐框坐标、分数、簇上下文、峰值坐标和标注图路径，深漏单独入档；每个目标模型每类失效落了至多 30 张标注图，在 output_det/struct_analysis/<目标>/viz/<类型>/ 下。初步抽查给了一个重要提醒：差分判定的 spurious 是"不被其它模型支持"，不等于"相对现实是错的"——有的 spurious 框住的物体真实存在，只是另外两个模型都没检出。这正是第三幕需要真值核验的原因，差分 oracle 的判定与相对真值的判定要分开陈述。

## 结构归因的模块化方向

结构归因最终做成独立模块，落在 evaluate/ 下。它不关心失效从哪来——自然差分、fuzzing 生成、腐蚀诱发，输入都是失效实例集合加目标模型，输出都是结构分析报告。现在的 struct_attr 模块加 run_struct_analysis 入口是它的雏形，等接口在几种输入源上稳定后再正式化。这是后话，先确认方向可行。

## 工作顺序

第一步，补全微观输出并人工抽查，建立失效判定与归因的可信度，这是其它一切的地基。第二步，检测版 profiling 与 fuzzing 适配，让第一幕的反馈循环转起来。第三步，正面验证（腐蚀诱发 + 真值裁判 + 签名收敛），不依赖微调、成本低。第四步，反面的修复实验，等模式可信后再投入。实验矩阵文档按这个顺序排，核心贡献顺着三幕定为两条：动态反馈驱动的检测失效发现与结构定位一体化框架；跨架构的结构失效签名发现。

后记（2026-06-11）：第一步在次日完成了系统化——真值核验把 200 张图的全部差分判定逐实例对照了 COCO 标注，agree 对照组正确率 91% 到 94%，三条结构签名在真值确认子集上全部存活，等于把第三幕"换裁判"的环节提前演练了一遍。结论与教训见同目录真值核验.md。核心贡献与实验矩阵随后正式锁定，见核心贡献与实验矩阵.md。
