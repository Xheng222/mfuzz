本清单覆盖从 2026-06-08 起的七天。目标是产出论文大纲或写作规划，而不是完成完整实验。这七天中的实验都按"探索 / 可行性验证"处理。每天产出一块可以写入大纲的内容。每完成一项，就勾选对应 checkbox。

## 背景与已定方向

项目从图像分类迁移到目标检测。分类版 mfuzz 框架已经完成差分行为、关键神经元覆盖、语义约束和联合优化四个模块，即 Phase 0 到 Phase 5。规格见 `docs/实现方案.md`，历史实验报告见 `docs/archive/`。

经与导师讨论，新方向确定为三点：迁移到目标检测模型；做结构分析，找出哪些层、哪些尺度、哪些区域和哪条分支容易出现缺陷；最终形成一篇论文。

本周需要确定的贡献声明如下：

> 提出一种内部反馈驱动的检测模型缺陷定位方法，把检测的四类失效（漏检、虚检、定位偏移、类别错误）归因到模型的具体结构位置：backbone 的哪一阶段、FPN 的哪个尺度、head 的分类分支还是回归分支、特征图的哪片空间区域，并给出"检测模型的缺陷在结构上集中在哪里"的系统证据。

论文的主要叙述是结构分析，多维反馈框架作为支撑方法。

## 框架通用性与两条风险

此前把"遥感数据集的标签空间对不上 COCO"视为主要风险。Day 2 之后，这个判断已经重新理解为设计要求，而不是风险。现实中，模型和数据集本来就按同域配对使用：YOLO、torchvision 这些 COCO 预训练模型在 COCO 上测试；专门训练来识别遥感目标的模型在遥感数据集上测试。不会把 YOLO 用来识别遥感数据，也不会让遥感模型在 COCO 上运行。因此，我们不做跨域实验，而是要求整套框架对"模型集合、数据集、标签空间"三元组参数化。COCO 不应固定写入任何环节。同一次实验中，这三者必须同域。换到其他域时，使用者需要提供该域上训练好的异构检测器集合和对应数据集，框架本身不需要修改。

核心方法本身具备通用性。consensus 聚簇、四类失效判定和结构归因，操作对象都是检测框和中间层激活，与具体识别什么物体、使用什么成像方式无关。真正需要保留接口的是每个模型家族的适配层：统一检测器接口负责加载模型、前向得到框/类别/分数，并暴露可以挂 hook 的中间层。torchvision 使用一个适配器，YOLO 使用一个适配器，以后接入遥感模型时再新增适配器。oracle 和归因层不需要修改。

Day 2 暴露出一个细节：标签空间如何定义，以及如何获取。每个模型家族暴露类别表的方式不同，即使都叫 COCO，索引约定也不同。torchvision 从 `weights.meta["categories"]` 取类别表，这是一份长度 91 的列表，索引 0 是 `__background__`，person 在索引 1，列表中还包含 11 个占位项（`__background__` 加 N/A）。YOLO 从 `model.names` 取类别表，这是一个长度 80 的字典，索引 0 直接是 person，没有占位项。同一个 person，在两边的索引分别是 1 和 0。因此，差分不能按索引比较，必须按类别名比较：先通过各自适配器拿到本地索引到类别名的映射，把每个模型的预测转换为类别名，再在类别名空间中聚簇和投票。一次实验的标准标签空间定义为参与模型类别名的交集，占位项先剔除。数据集如果带真值并用于 TIDE 式校验，也需要按类别名映射到同一空间。Day 2 的 pilot 使用的三个模型全部来自 torchvision，共享同一份 91 类列表，所以按索引比较没有暴露问题；一旦加入 YOLO，按名对齐的适配层就是必须项。

还剩一条真正的前置条件：差分分支在任何域都需要至少两个共享同一标签空间的异构检测器。COCO 上 torchvision 已经提供多个可用模型。换到遥感域时，现成的、共享同一套标签空间的异构预训练检测器不一定容易凑齐。mmrotate 这类模型库中的架构和类别定义经常不同。框架支持任意域这个声明在方法层面成立，但差分分支能否在某个域实际运行，取决于该域是否具备可用的异构模型集合。这是使用者需要满足的前置条件，论文中说明即可。

另一条风险是 YOLO 的内部激活访问。Day 2 已经解除这个风险。`yolo11n` 底层是标准 `nn.Module`，88 个 Conv2d 层全部可以挂 forward hook，骨干、neck 和头部都能覆盖。唯一需要适配的是层命名，例如 `model.0.conv` 这种风格与 torchvision 不同。这属于模型家族适配层的工作。详见 `docs/paper_plan/Day2/检测迁移可行性.md`。
