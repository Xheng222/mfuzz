### struct_attr.py（模块 2）

grad×act 归因公式与 spec 一致，未发现违反公式的偏差：

- [假设] |grad×act| 对全维求和、按桶归一化成份额（struct_attr.py:177-181），与 Day4 结构分析方法.md 第 9 行一致。
- [假设] 责任尺度取各 FPN 特征梯度绝对值和的非零最大者（:184-191），只用梯度不乘激活，与 spec 文字一致。
- [假设] 空间峰值图在责任层级做 |grad×act| 后对通道维求和取 argmax（:205），与 Day4 第 13 行一致。
- [假设] backbone 桶份额被层规模主导，spec 建议报相对 agree 的比值；该修正在下游 det_analysis.py:322-326，属设计分工。
- [结论]（已复核；cls 部分已由代码修订）归因目标偏离 spec 的 NMS 前 logit。原先 cls/spurious/agree 都用后处理概率 `g.scores_g[idx]`。实验流已把 **cls** 改用 logit-link 目标 `log(p)-log1p(-p)`（struct_attr.py `cls_logit_target`、`_make_target`），对 sigmoid 头（retinanet/fcos）等价于 NMS 前 logit、cls 偏离实质消除（fcos 另乘 centerness，属近似）；**spurious/agree 仍用概率 scores_g**，仍偏离 spec，但这两类用概率的归因本就有效（虚检/漏检可分），暂按可接受处理。三检测器共用 `forward_graph`（det_models.py:157-178），scores_g 取后处理输出（faster_rcnn softmax、retinanet/fcos sigmoid）。两人确认：核实 worker + 调度者独立读 det_models.py。
- [假设] 用概率而非 logit 可能是误分类归因弱的成因：高置信时 sigmoid/softmax 导数 σ(1-σ) 趋零，压低 grad×act。待实验改用 logit 目标重跑、看责任通道与随机对照可分性是否改善。

### unit_coverage.py（模块 3）

账本累加与 spec 第七节、研究方案 2.1/2.2、Day3 结构分解规格.md、Day5 覆盖标定首跑.md 一致，未发现违反公式的偏差。spec 第七节只有文字描述，正式公式在 docs/materials/研究方案.md（CL/CNCov/obj_cov）。t/k 分离与分位关键度是有据的设计决策（Day3:55、coverage.py:9-18、profiler.py:_critical_mask），已核对依据，不当作 bug。以下边界与实现细节记为 [假设] 待复核：

- [假设] 覆盖判定 `norm_critical(v) > t_cov` 后 `any(dim=0)`、`covered |= hit`，只增不减（unit_coverage.py:99-104）。对应 spec"存在某测试样本使关键单元归一化激活超阈值即覆盖"（研究方案 2.2），算式与单调性一致。
- [假设] 单元粒度＝层名×调用序×通道，激活向量按布局把每个 (层,调用) 的 Conv 输出做 GAP（对 batch+空间维 mean）得逐通道标量（detection.py:_gap_vector:186-195、_build_layout:60-62）。与 Day3:53 通道级 GAP、空间维不进账本一致。
- [假设] 归一化是全局逐单元 min-max：low/high 由整个标定集累计（detection.py:147-148 torch.minimum/maximum），运行时 `(v-low)/(high-low+EPS)`（unit_coverage.py:89-97）。与 spec 第七节"按 profiling 区间做 min-max 归一化"一致。注意这与 CriticalFuzz 原版的 per-image scale（criticalfuzz/coverage.py:scale:61-74、get_critial_neuron.py:351）不同——CriticalFuzz 每张图各自 min-max，mfuzz 用全局区间，更接近 DeepGauge profiling。spec 文字采用全局区间，属有据选择。
- [假设] 频率项 `freq = (norm > t_freq).float().mean(dim=0)`（build_frequency_profile:73）／流式版 `cnts[t] += (norm>t).float()` 再除 n_ok（detection.py:_freq_pass:100-107）。spec 公式 `Freq(out(n,T)>t)` 写的是原始 out，mfuzz 在归一化后的 norm 上比较；coverage.py:9-14 说明频率与覆盖共用同一套归一化标度，是有意为之，不算偏离，但与 spec 字面 `out>t` 有标度差，记此供复核。
- [假设]（模块 4 复核，倾向"有意的标度统一、非偏离"）频率与 obj_cov 用归一化 norm 而非 spec 字面 out 一节，复核认定是有意设计：profiler.py docstring（:23-31）与 coverage.py docstring（:9-18）都明确写"频率、覆盖判定、覆盖目标、缺陷指纹共用同一套逐单元 min-max 归一化 ĉ"，理由是各层激活量纲差异大、固定阈值 t 直接作用在原始 out 上会让某些层几乎全激活、某些层几乎不激活，归一化后 t 表示"爬到自身区间几成高"对所有层含义一致。检测侧同理：profile_from_stats、_freq_pass、norm_critical、objective 全在 norm 上算，标度自洽。spec 公式写 out 是抽象记法，实现统一加了归一化层，属有据的工程选择，不算正确性偏离。建议在 spec 第七节补一句"频率与 obj_cov 中的 out 实指归一化激活 ĉ"以消除字面歧义。
- [假设] 关键度＝频率达 critical_tau 分位且区间非退化：`q=quantile(freq,tau); mask=(freq>=q)&(high>low)`（profile_from_stats:59-60）。对应研究方案 2.1"关键度超阈值 τ 纳入 D_en"，这里用分位而非绝对阈值，依据见 profiler.py:_critical_mask:87-94（绝对阈值跨层不可比、分布偏 0），是有据设计。
- [假设]（模块 4 复核，倾向"应统一但非数据正确性 bug"）边界不一致：检测侧 profile_from_stats 用 `freq >= q`（含等于分位，unit_coverage.py:60），分类侧 profiler._critical_mask 用 `cl > thr`（严格大于，profiler.py:94）。两处都是"取分位以上"，方向一致，但等于分位时归属相反。复核结论：这是两套独立账本的两条独立代码，分类侧用连续的融合关键度 cl（频率与百分位归因加权，profiler.py:420），打结概率低，>= 与 > 实际差别小；检测侧 freq 是离散占比（图数比值），`freq==0`/`==1` 与中间档大量打结，分位若落在打结值上，>= 把整条打结带全选进、> 把它全剔出，选出单元数可在打结处跳变，对 critical_tau 更敏感。两边内部各自自洽（同一函数判覆盖与判关键用同一不等号方向），不构成"标定与运行时对不上"的错误，但跨任务边界约定不一致、且检测侧在打结处更脆，建议统一为同一约定（倾向都用 `>=` 取分位以上，含义更贴合"达到该分位"）。是否改由调度者定。
- [假设] `high > low` 过滤掉恒定单元（区间退化），呼应 normalize_acts 对 high==low 的 nan_to_num 兜底（profiler.py:64-71）。spec 未明文要求，属合理边界处理。
- [假设] select_u 默认从未覆盖关键单元里取批内归一化激活最高的 U 个（unit_coverage.py:115-126），objective 取 U 单元归一化激活之和（:128-130）。对应 spec obj_cov＝∑_{n∈U} out(n,x)（研究方案 2.3 式），区别是 mfuzz 用归一化激活而非原始 out；选 U "接近阈值且信号强"在此实现为"当前归一化激活最高"，与 spec"优先接近激活阈值"方向相符但不完全等同（最高未必最接近阈值）。记此供复核。
- [假设]（可优化，本轮不改）_freq_pass 对每个 t 档都重算一遍 `(norm>t).float()` 并整向量累加，t_list 多档时重复遍历单元向量；可一次性对 t_list 做广播比较省内存带宽。属性能优化，非正确性问题。

### 标定阈值是否被使用（模块 4）

核心结论：标定环节产出的统计量与阈值确实在运行时被使用，链路一致、无断点、无"标定了却没用上"或"用了另一套值"的情况。检测侧三个阈值各有清晰来源与用法，全部按 spec 第七节"按 profiling 区间 min-max 归一化后判覆盖、频率阈值标定、覆盖阈值运行时判断、两者独立"的定义工作。核心结论经调度者独立读代码复核（detection.py:110/130/343-355、unit_coverage.py:54-61/89-104、base.toml [coverage]），升为 [结论]（已复核）；其余分项仍记为 [假设] 待复核：

- [结论]（核心结论，已复核）标定产物与运行时读同一份缓存、同一组装函数，参数链路闭合。标定脚本 calibrate_det_tcov.py 和运行时 build_tracker 都调用同一个 build_det_profile（detection.py:110）建/载缓存，缓存键＝目标模型×标定集目录名×图数（detection.py:130 `det_{target}_{tag}_n{len}.pt`），存 layout/low/high/多档 freq；都用同一个 profile_from_stats（unit_coverage.py:54）从缓存组装关键集合。标定脚本只是在缓存之上对 (t_freq, critical_tau, t_cov) 做网格离线扫描报 CNCov_0（calibrate_det_tcov.py:81-104），不回写配置；运行时按 cfg.coverage 的单组定值组装（detection.py:347-348、:355）。两条路径共用缓存与组装代码，所以"扫描时看到的某组合"与"运行时用该组合"产出的关键集合、归一化界完全一致。
- [假设] profiling 的逐单元 low/high 区间：标定第一遍流式 torch.minimum/maximum 求每单元 min/max（detection.py:147-148），存入缓存。运行时 UnitCoverageTracker 从 profile.low/high 取这套界做归一化（unit_coverage.py:84-85、:89-97），覆盖判定、obj_cov、select_u、ood_units 探针全用它。确为标定产物驱动运行时，无写死默认。
- [假设] t_freq（频率激活阈值）：标定时决定频率统计的档位。检测侧标定 build_det_profile 默认按 _T_FREQ_GRID=(0.3,0.5,0.7) 多档同时统计并缓存（detection.py:67、:153），运行时按 cfg.coverage.t_freq 取对应那档 freq；配置档不在网格里时单独补算一遍再缓存（detection.py:165-179）。base.toml 写 t_freq=0.5（configs/det/base.toml:20），恰在网格内，直接命中缓存档。t_freq 只进关键集合的选取，不进覆盖判定，与 spec"频率阈值用于标定"一致。
- [假设] critical_tau（关键度分位）：是 profile_from_stats 的事后参数，不进缓存（detection.py:124 注释明确），运行时按 cfg.coverage.critical_tau 在缓存的 freq 上取分位定关键集合（detection.py:180-181）。base.toml 写 critical_tau=0.5。标定脚本把它当扫描维（GRID_TAU=(0.3,0.5,0.7)）报不同 tau 下的关键单元数与 CNCov_0，供人工选档。改 tau 不需重跑前向、秒级出网格，设计合理。
- [假设] t_cov（覆盖判定阈值）：完全是运行时参数，既不进 profiling 缓存、也不影响关键集合，只在 UnitCoverageTracker.update 判覆盖时用（unit_coverage.py:101 `norm_critical > self.t_cov`）。从 cfg.coverage.t_cov 直接传入构造器（detection.py:355）。base.toml 写 t_cov=0.85，注释记录这是 train2017 全量标定 + 63 组网格扫描定参的结果（configs/det/base.toml:21-23），标定脚本的扫描档位 GRID_TCOV 含 0.85（calibrate_det_tcov.py:29）。t_cov 与 t_freq 解耦、且 t_cov(0.85) > t_freq(0.5)，与 spec 第七节、coverage.py:12-18"覆盖阈值取得比频率阈值高、避免初始饱和"完全一致。
- [假设] 配置回填方式是人工而非自动。两个标定脚本都只报告分布/建议值、不自动改配置：calibrate_det_tcov.py 把网格结果落 JSON 到 output/det/tcov_scan/ 供人看（:105-106），calibrate_thresholds.py 末尾明说"按需手填进配置"（calibrate_thresholds.py:202-205）。这与 spec 文字一致（spec 第九节配置体系是手写 TOML，第十二节记 t_cov=0.85 是网格定参后写入 base.toml）。即标定→选值→手填配置→运行时读，链路靠人接一道，但代码侧读写都指向同一处，无歧义。
- [假设] 所有 det 配置变体的覆盖阈值都继承 base：扫描全部 configs/det/*.toml，只有 base.toml 定义 [coverage] 三阈值，diff/scale_diff 仅改 lambda2，其余变体不碰 coverage 节（grep 确认），都经 extends 继承 base 的 t_freq=0.5/t_cov=0.85/critical_tau=0.5。无某变体偷偷换一套覆盖阈值的情况。
- [假设] 分类侧标定阈值同样被运行时使用，链路与检测对称。profiler.build_profile 把 t（=t_freq）、tau、alpha 等连同 low/high/freq/cl/critical 一起算出并缓存，缓存键含 model/dataset/val_fraction/t/tau/tau_class/alpha/p_low/p_high/classes（profiler.py:376-390）；t_cov 不进缓存、由 CoverageTracker 构造器从 config 直接传入（coverage.py:37-39 注释明确"改 t_cov 不该让 profile 缓存失效"）。profile_neurons.py、calibrate_thresholds.py 读同一份缓存、用 cl_percentiles/ratio_at 报不同 tau 下占比供选档（profiler.py:150-158）。与检测侧同构。
- [假设]（轻微，记此供留意）冒烟配置 smoke.toml 用 profile_dir=""、profile_images=10 走 image_dir 尾部兼容路径（configs/det/smoke.toml:21-22、detection.py:336-342），标定样本量很小，频率统计噪声大、关键集合不稳，但 docstring 与配置注释都标明这只供冒烟、不出数（det_analysis.py:40-43、configs/det/base.toml profile 注释）。非正确性问题，属已知设计。
