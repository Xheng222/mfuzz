# 调度规范

调度者负责一组工作流，派发 worker、检查成果，并决定合并。提交和合并是两件事：各工作流提交自己的结果，调度者只决定与执行合并。合并权只属于调度者，因为调度者掌握全局进度，一次只处理一条工作流，避免多个成果同时进入主线。

## 提交结果，不提交过程

核心原则是提交结果、不提交调度过程。工作流产出的是结果，值得提交；调度本身是过程——派发、检查、等待、查进度——这些没有留存价值，所以调度者不为自己的活动留提交。

- 各工作流提交自己的结果，在自己的线上，按"一个结果完成"来提交，频率和粒度自己定。
- 调度者本身不提交。它的价值在协调与决定，不在留下自己的活动记录。
- 当调度者亲自做某条工作流（没有单独派 worker）时，它以那条工作流的身份提交结果。

## 角色分工

| 角色 | 职责 | 边界 |
|------|------|------|
| worker | 在指定工作区产出成果；一个结果完成就在自己工作区里自行提交（粒度、频率自定）；更新自己的工作流文件，把结果返回调度者 | 不合并进 linux |
| 调度者 | 派发、检查；按判断标准决定何时把工作流结果合并进 linux；合并前向用户声明、经同意后再合并；维护协调用的调度文件 | 本身不提交；不直接执行 worker 的具体任务 |

## 状态写入时机

状态文件（各工作流文件、BOARD、调度文件）随做随写、留在工作区即可，不要留到会话结束。jj 会对工作副本快照，会话中断也能从工作区读到未提交的改动。

写状态文件、提交、合并是三件不同的事：写是随时的；提交由各工作流按"结果完成"自行决定；合并由调度者按下面的判断标准、经用户同意后才做。调度者更新 BOARD 和自己的调度文件属于"写状态"，不等于提交。

## 合并的判断标准

调度者用一套标准决定何时把工作流的结果合并进 linux。看产出，不看动作。一个值得合并的里程碑，是"一段工作产生了稳定的、下一步要依赖的产出"，而不是"做了一个动作"。在那之前都算中间步。

三个判断问题，有一个为"是"才考虑合并：

1. 结果出来了而且解读完了吗？（只是启动了、还在跑，不算）
2. 做了一个会改变下一步怎么做的决定吗？
3. 一个具体交付物完成了吗？（代码验证过、文档某节写完、worker 成果检查过）

反面清单（这些是过程，不触发合并，只更新状态文件）：启动或排队作业、同步代码、读一次中间产物、确认某东西起跑、改一行队列或 owner、跑中途的进度查看。

判断窍门：当"我们现在知道了什么、决定了什么"往前走了一步，才提议合并；只是"我刚做了什么"变了，不合并。

## 合并前的声明

每次把结果合并进 linux 之前，调度者必须先向用户声明：要合并哪条工作流的什么内容、为什么现在合并。用户同意之后才能合并。合并后向用户汇报合并内容；结论的升级和删除单独说明。

## BOARD 与调度文件的去向

BOARD 与调度文件是协调用的草稿，不单独提交。平时留在工作区随时更新；当某次经用户同意的结果合并发生时，把当时 BOARD 的整合状态（GPU 队列、各工作流 status、指针）随那次合并一并带进 linux。进 linux 的永远是"结果加配套的状态"，不是"调度了一步"。

## 每日开始

工作分为三层：

| 层级 | 文件 | 用途 |
|------|------|------|
| 总体顺序 | `docs/paper_plan/路线图.md` | 记录总故事和推进顺序 |
| 工作流待办 | 各工作流文件中的"作业队列" | 记录该工作流的长期待办 |
| 今日任务 | 调度文件中的"今日计划" | 记录当天从各工作流队列中选出的任务，只引用队列项，不重复抄写内容 |

每日开始时：

1. 读取 `BOARD.md`、自己负责的工作流文件和自己的调度文件，确认当前进度。
2. 对照路线图当前阶段和各工作流队列，提出当天值得推进的任务，写成"今日计划"。
3. 把"今日计划"交给用户确认。这是一道硬性关口：没有得到用户确认之前，不派发任何 worker，也不改动各工作流的 `owner`。用户确认之后，才进入下一步。
4. 检查并调整各 worker 的工作流文件。
5. 按计划把任务派发给 worker，并指定对应工作区。

## 每日结束与会话交接

1. 检查当天 worker 的成果。
2. 先把记录写完整，再清理上下文：更新各工作流文件（已确认的结论追加到"已知上下文"并标"已复核"，作业队列更新到下一步，清理 yaml 区状态）与调度文件；同时把不适合进入上下文的内容去掉——过程流水、一次性操作细节、可从代码或提交历史得到的叙述、与正式文档或他处重复的内容，都不留在状态文件里，只保留决定、当前事实、已验证的结论与待验证的假设，以及指向正式产物的指针。
3. 判断是否有该合并进 linux 的结果：有就向用户声明、经同意后合并一次完整一致的状态；没有就让结果留在各工作流，状态文件留在工作区作为草稿。
4. 向用户汇报工作内容。

## 向 worker 派发任务

工作流的认领和释放规则见 `BOARD.md`。本节只说明调度者派发任务时需要补充的内容。

1. 选择一条未被占用的工作流，并按 `BOARD.md` 的规则完成认领。
2. 编写任务说明与调整工作流文件。任务说明需要包含工作区路径、工作流文件、具体任务、相关代码和文档、完成标准、成果写入位置，以及状态写回该工作区内的哪条工作流文件。worker 完成一个结果后在自己工作区里提交。任务说明要给出工作区的**绝对路径**，并要求 worker 第一步先 `cd` 到该路径、用 `pwd` 确认确实在工作区内（而不是主检出），够不到就停下报错。否则 worker 会把工作区名当相对路径，回落到主检出里干活，成果落错地方。
3. 如果任务需要使用实验服务器，先查看 `BOARD.md` 中的 GPU 队列。实验作业按照提交顺序排队，再派发给 worker。

> worker 是子 agent，可以读取启动者主检出中的 `CLAUDE.md` 和 memory，任务说明不需要重复这些规范。前提是本项目使用 jj 管理工作区，而不是使用框架自带的 worktree 隔离。

## 检查与合并

worker 返回的结果只有调度者能看到。调度者需要先把关键信息转告用户，然后处理成果。

1. 按完成标准检查成果。成果不合格时，启动新 worker 继续推进。
2. 复核 worker 对"已知上下文"的改动。调度者作为第二个确认者，独立核查新升级的结论和被删除的条目；必要时重新运行相关步骤，不能只根据 worker 的叙述判断。后续工作会依赖的重要结论，可以再安排一个冷启动审查 worker 独立复核。复核结果要写进工作流的"记录"。这一步是否做、是否追求把假设升为结论，按用户的取向；用户不要求复核时，结果可以保留为弱假设。
3. 成果合格、且该工作流文件与调度文件的相关记录都已写完整后，按"合并的判断标准"判断是否到了合并时机。
4. 按"分支同步与合并"一节执行合并。
5. 向用户汇报合并内容。结论的升级和删除需要单独说明。
6. 如果这条工作流还要继续，继续派发 worker；如果已经完成，把 `status` 改成 `done`。

合并只由调度者执行，并且一次只处理一条工作流，因此不会出现多个成果同时合并的情况。

## 分支同步与合并

主分支是 `linux` bookmark。所有工作区，包括主检出，地位相同：每个工作区都从当前 `linux` 头开始，在自己的工作流上保持线性提交。本节描述的是经用户同意、要执行合并时怎么做。

每次同步分两步，所有分支使用同一套做法：

1. 确定新的 `linux` 头。选择一条分支的最新提交作为新头，并在那条分支的工作区中把 `linux` bookmark 移到该提交上。这条分支完成同步，不再做其他操作。
2. 其余分支在各自工作区目录内，把自己的工作 rebase 到新的 `linux` 头上。各工作流修改的路径不相交时，rebase 应当不产生冲突。

如果某条分支没有新改动，第二步会简化：它没有需要 rebase 的内容，只需要在新头上 `jj new` 一个空提交，然后继续使用。任何空闲分支都适用这一规则；主检出只是最常处于这种状态，所以常被用作例子。

只有两条分支修改同一个文件时，才会出现冲突。出现冲突时，jj 会给出带标记的冲突内容，需要在对应文件中解决。

jj 在 rebase（以及多数命令）开始时会先对工作副本做快照，这带来一个合并顺序的坑：被忽略的引导文件（例如工作区指向主检出的符号链接）一旦在某工作区的 `.gitignore` 里还没被忽略，rebase 时就会被快照进提交。合并前要先确认每个工作区的 `.gitignore` 已忽略这些文件，再 rebase；若某文件已经被快照进提交，用 `jj file untrack <路径>` 摘掉。

## 多个调度者的协作

可以同时存在多个调度者。它们通过共享状态文件避免冲突。

1. 同一类信息只记录在一个地方。工作流是否被占用，读取对应工作流的 `owner`；GPU 上运行什么作业，查看 `BOARD.md` 中的队列；调度者自己的进度，读取自己的调度文件。
2. 调度者之间不直接通信，而是通过读取共享文件错开任务。派发 worker 前，先检查工作流的 `owner`；如果已经被占用，就避开这条工作流。
3. GPU 一次只运行一个作业。所有实验任务都按照 `BOARD.md` 中的 GPU 队列排队，作业完成后再让出资源。

用户负责最上层的安排。用户可以打开多个调度者会话，并给每个调度者分配一组工作流。每个调度者都需要在 `BOARD.md` 的活跃调度者表中登记一行。调度者之间不需要再设置更高一层的调度者。
