# BOARD

本文件是多会话状态的总入口。仓库保存真实记录，会话只负责执行。需要后续会话继续使用的信息，都写入状态文件。调度规则见 `调度规范.md`。

## 状态写入时机

状态只记录已经发生、可以观测的动作。不要等到会话结束再保存信息，因为会话可能随时中断。

- worker 完成任务后，更新对应工作流文件。
- 调度者完成派发、检查或合并后，更新自己的调度文件。

## 工作区

每条工作流使用一个长期复用的 jj 工作区。工作区位于主检出之外，保存对应工作流的成果。共享数据通过符号链接从主检出接入。

| 流 | 工作区 |
|----|--------|
| 实验 | `F:/doc/安全缺陷/工作区/实验` |
| 写作 | `F:/doc/安全缺陷/工作区/写作` |
| 可视化 | `F:/doc/安全缺陷/工作区/可视化` |
| 审计 | `F:/doc/安全缺陷/工作区/审计` |

工作区遵循以下约定：

- 新建工作区后，先运行引导操作，把 `output_det`、`references`、`datasets` 和 `.venv` 符号链接到主检出。这四个名字已经写入 `.gitignore`，jj 不跟踪这些链接。
- 快照、提交、rebase 等 jj 操作，都在对应工作区目录内执行。
- 调度者一般只在主检出中修改自己的调度文件，不在主检出中修改各工作流的状态文件，当需要时，应该在对应工作区中修改。各工作流各自在自身工作区里修改工作流状态文件，且仅能修改自己的状态文件。这样可以避免不同工作流之间的状态冲突。
- 实验需要把源码同步到服务器时，从各自的工作区运行 `sync_lab.ps1`。脚本按相对路径执行，不受工作区位置影响。
- 成果的提交和合并只由调度者执行。worker 不提交成果。规则见 `调度规范.md`。

## 工作流文件格式

每条工作流对应一个文件，位置是 `streams/<名字>.md`。文件应包含接手所需的信息。新的会话读取该文件和其中指向的产物后，应该可以继续处理这条工作流。

工作流文件的头部字段如下：

| 字段 | 含义 | 取值 |
|------|------|------|
| `stream` | 工作流名字 | 与文件名一致 |
| `owner` | 当前负责人 | 负责人标签；空闲写 `none` |
| `status` | 进度 | `idle` / `in-progress` / `blocked` / `done` |
| `updated` | 最后改动时间 | 日期 |

正文小节按照以下顺序排列：目标、已知上下文、作业队列与下一步、阻塞、记录、指针。"记录"只追加，不删除。每条记录单独写一行，说明操作、结果和产物位置。"已知上下文"的写法见下一节。

## 已知上下文

每条工作流的"已知上下文"用于保存当前有效、但不能直接从代码中读出的信息。worker 接手任务时，需要先读取这一节。

"记录"保存历史，只追加，不删除。"已知上下文"保存当前认识，可以随着项目变化新增或删除。历史已经留在"记录"里，过时条目可以从"已知上下文"删除。

每条上下文写成一行，并带一个类型标签：

| 标签 | 内容 |
|------|------|
| 决定 | 已经确定的选择及其理由 |
| 方法 | 为了保持前后一致，需要继续遵守的协议 |
| 设定 | 关键参数值 |
| 结论 | 已经验证为真的发现，需要带"已复核"标记 |
| 假设 | 暂定、仍待验证的判断 |
| 坑 | 操作陷阱和容易出错的地方 |

上下文条目按以下方式维护：

- 新增：发现一条当前有效、且不能直接从代码中读出的信息时，写入"已知上下文"。
- 升级：假设经过验证后，可以升级为结论。结论升级需要复核，规则见下文。
- 删除：条目被推翻、被取代、受底层代码变化影响，或者已经转入正式文档或代码时，从"已知上下文"删除，并在"记录"里说明删除内容和删除原因。
- 转入正式位置：结论稳定到应该进入正式文档或代码时，移动到对应位置。"已知上下文"只保留指向正式位置的指针。

"已知上下文"只保存对应工作流专有的信息。跨工作流的项目级决定放在路线图或 memory 中；需要引用时写出指针，不要重复记录。

结论升级需要两次确认：

- 产出结论的 worker 完成第一次确认，独立复核的审查者完成第二次确认。没有通过第二次确认的内容，一直保留为假设。
- 审查者需要独立核查当前产物，必要时重新运行相关步骤。审查者不能只阅读叙述后表示同意。worker 和审查者必须是不同的 agent。
- 默认审查者是调度者。后续工作会依赖的重要结论，需要再安排一个冷启动的审查 worker 复核，并在提交汇报中告诉用户。删除结论时也使用同样规则。
- 复核结果需要写入"记录"。"已知上下文"中的结论只标记"已复核"，不附带证据。

## 认领与释放工作流

认领一条工作流：

1. 读取目标工作流的 `owner`。
2. 如果 `owner` 不是 `none`，说明已有会话在处理这条工作流，应当换一条。
3. 如果 `owner` 是 `none`，把 `owner` 改成认领者标签，并把 `status` 改成 `in-progress`。

释放一条工作流：

1. 把进展追加到"记录"。
2. 更新"已知上下文"、`status` 和 `updated`。
3. 把 `owner` 改回 `none`。
4. 如果有调度者负责这条工作流，把结果返回给调度者。

> `owner` 是约定标记，不是锁。它用于避免两个会话同时认领同一条工作流。工具不会强制执行这个约定，所以认领前必须主动检查；如果已经被占用，就换一条。
